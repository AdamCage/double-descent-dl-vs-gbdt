# s05. Чистый MLP на матрице 4099

Статус: процесс жив. Ширину 256 не прерывать. Код этапа не редактировать. Второй прогон не ставить. GPU не занимать.

## Назначение

Снять model-wise кривую чистых меток по заранее заданным ширинам и, внутри той же команды, epoch-wise кривую самой широкой сети. После точек ширин 8–128 назначение сужено: это запись насыщения, а не поиск интерполяционного пика. Пик ищут в [b01-controlled-double-descent.md](b01-controlled-double-descent.md), на другой постановке.

Шумовое плечо 10% в этом процессе выключено. Включать его на этих же файлах нельзя: сравнение с CatBoost идёт только при нулевом шуме.

Архитектура: Linear → ReLU → Linear → ReLU → Linear → один логит, BCE-with-logits. Accuracy в мониторе — порог 0.5.

## Выходы

Пока `run()` не вернулся, устойчивая запись — строки лога. Код не пишет json после каждой ширины. В конце model-wise цикла, ещё до epoch-wise, рисуются `model_wise_logloss` и `model_wise_accuracy`. Это случится только после последней ширины списка, не после 256.

Когда функция дойдёт до конца, каталог `result/05_dnn` получит `dnn_results.json`, `model_selection.json`, `best_model.pt` (ширина, выбранная для сравнения), `epochwise_model.pt` (самая широкая, не модель сравнения) и `cache_hash.json`. В json model-wise попадает последняя записанная точка каждой ширины, число записанных точек и флаг `optimization_settled`. Сама траектория по эпохам для model-wise на диск не кладётся: шаг записи — `epochs // 20`, то есть 40 эпох, и список живёт только в памяти процесса.

Ключ кэша считается в начале `run()` и включает константу `review-2026-11-04`, хеш файла `s05_dnn_train.py` и хеши матрицы и меток. Поэтому файл этапа и `src/protocol.py` сейчас не правятся.

Выбор модели сравнения, когда json появится: минимум validation loss среди ширин с `settled=True`. Если таких нет — минимум validation loss и явное имя правила `no_width_settled_best_validation_logloss`. Самая широкая сеть в это правило не подставляется автоматически.

## Критерий pass/fail

Научное чтение плеча, не инженерный конец функции:

- В логе есть финальные строки ширин 8, 16, 32, 64, 128. Они уже есть. Validation loss монотонен: 0.0063, 0.0048, 0.0037, 0.0025, 0.0023. Train accuracy на всех пяти — 1.000. Val accuracy — 0.999, 0.999, 0.999, 1.000, 1.000.
- Ширина 256 обязана получить такую же финальную строку. Пока её нет, кривая шире 128 не интерпретируется.
- Pass отрицательного результата: на этих ширинах нет участка роста validation loss, а левый край уже с train accuracy 1.000. Это не double descent.
- Инженерный конец этапа — `dnn_results.json` и `cache_hash.json` после всего списка ширин и epoch-wise. Его отсутствие при живом процессе не есть fail науки и не есть повод к остановке.

`settled=False` на ширинах 16 и 128 при train accuracy 1.000 означает только, что на последней пятой записанных точек train loss ещё сдвинулся больше чем на 5% относительно. Это не провал интерполяции.

## Что нельзя утверждать

Что кривая 8–128 — double descent, epoch-wise double descent или позднее ускорение. Что val accuracy 0.999–1.000 измерена на test. Что следующая ширина «должна» дать пик. Что шум 10% на этой матрице задним числом создаст научный double descent. Что результат переносится на другой корпус или другой эмбеддер.
